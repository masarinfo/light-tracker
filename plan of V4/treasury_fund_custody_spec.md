# وحدة إدارة الخزينة والتحكم بالأموال (Treasury & Fund Custody Module)
## جزء من المعيار الموحّد (Standard Architecture)

> **السياق:** بما أن النظام غير مرتبط بأي بوابة دفع مركزية (لا Custodian ثالث)، فإن **المسؤولية الكاملة عن أمان الأموال بعد وصولها تقع على البنية التي نصممها هنا**. هذا القسم لا يقل أهمية عن وحدة الاستقبال نفسها — بل أخطر، لأن أي خلل هنا يعني خسارة مباشرة ونهائية للأموال (لا رجعة فيها على البلوكشين).

---

## 1. المشكلة بالضبط

بعد وحدة الدفع، الأموال تصل لعناوين متفرقة **مولّدة تلقائياً واحد لكل فاتورة** (حسب تصميم الوحدة السابقة). هذا ممتاز للمطابقة التلقائية، لكنه يخلق تحدي جديد:

- آلاف العناوين المتناثرة عبر 6 شبكات = صعوبة إدارة ومراقبة يدوية
- كل عنوان يحتوي مفتاح خاص (Private Key) يجب حمايته
- الأموال "نائمة" بعناوين استقبال، غير مُستثمرة أو مُستخدمة، وغير محمية بنفس مستوى خزينة مركزية

**الحل المعياري المحدَّث: محفظة تشغيلية واحدة آلية بالكامل (Automated Single Operational Wallet)**

> بما إن قيم الاشتراكات صغيرة جداً (أعلى فئة $50)، لا داعي لهيكلية 3 طبقات مع موافقة يدوية على كل سحب — هذا Overhead إداري غير متناسب مع حجم المبالغ. البديل: محفظة تشغيلية واحدة لكل (شبكة + عملة)، برصيد مستهدف ثابت (Target Float Balance)، تُغذَّى تلقائياً من عمليات الكنس، وتُنفِّذ السحوبات الصغيرة (استرجاع، عمولة مسوّق) **تلقائياً بدون موافقة يدوية**، طالما ضمن سقوف أمان محددة.

```
┌─────────────────────────────────────────────────────────┐
│  عناوين الاستقبال (Deposit Addresses)                      │
│  - عنوان فريد لكل فاتورة، تُكنس تلقائياً فور تأكيد الدفع       │
└───────────────────┬───────────────────────────────────┘
                     │ كنس تلقائي (يغذّي المحفظة التشغيلية)
                     ▼
┌─────────────────────────────────────────────────────────┐
│  المحفظة التشغيلية الآلية (Operational Wallet)                │
│  - محفظة واحدة لكل (شبكة، عملة) — رصيد مستهدف ثابت (Target)   │
│  - كل الإيداعات تدخل هنا، كل السحوبات الصغيرة تخرج من هنا تلقائياً │
│  - سقف أمان مزدوج يحكم الأتمتة (راجع القوانين الصارمة أدناه)   │
└───────────────────┬───────────────────────────────────┘
                     │ فائض فوق الرصيد المستهدف يُرحَّل تلقائياً
                     ▼
┌─────────────────────────────────────────────────────────┐
│  احتياطي التجميع (Reserve Wallet)                           │
│  - يستقبل أي فائض تلقائياً (تراكم الأرباح الفعلي)              │
│  - تغذية المحفظة التشغيلية منه تتم يدوياً فقط عند الحاجة       │
│    (نادرة الحدوث لأن الرصيد المستهدف يُحسب بهامش كافٍ أصلاً)    │
└─────────────────────────────────────────────────────────┘
```

> **ملاحظة:** المحفظة التشغيلية تبقى "ساخنة" (متصلة بالسيرفر) لأنها تحتاج التوقيع الآلي، لكن **مبلغ التعرض القصوى محدود دائماً بالرصيد المستهدف + سقف السحب اليومي** (موضّحين بالقوانين أدناه) — هذا يحوّل "مخاطرة اختراق كارثية" إلى "مخاطرة محدودة بسقف معروف مسبقاً".

## 2. آلية الكنس التلقائي (Sweep Mechanism)

**متى تُشغَّل:**
- فوراً بعد أن تصل فاتورة لحالة `PAID` (Event-driven) — **وليس فقط بجدولة زمنية**، لتقليل نافذة التعرض للخطر لأقل مدة ممكنة.
- جدولة احتياطية إضافية كل ساعة، تفحص أي عنوان استقبال به رصيد متبقٍ لم يُكنس (لأي سبب فشل).

**آلية العمل لكل شبكة:**
```
1. النظام يجلب كل blockchain_transactions المؤكدة (CONFIRMED) غير المكنوسة (swept_at IS NULL)
2. لكل عنوان: يُشتق مفتاحه الخاص لحظياً من الـ HD Wallet (لا يُخزَّن أبداً بقاعدة البيانات)
3. يُبنى ويُوقَّع Transaction تحويل كامل الرصيد → عنوان المحفظة التشغيلية الساخنة (Layer 2)
4. عند نجاح البث (Broadcast) والتأكيد → يُسجَّل sweep_tx_hash + swept_at
5. المفتاح الخاص المُشتق يُمحى من الذاكرة فوراً بعد الاستخدام (Zero-out)
```

> **قاعدة صارمة — حاسمة:** المفتاح الخاص لأي عنوان استقبال **لا يُخزَّن أبداً بشكل صريح بقاعدة البيانات أو أي ملف**. يُشتق فقط لحظة الحاجة من الـ Master Seed (المخزّن مشفّراً بخزينة أسرار مخصصة — HashiCorp Vault أو AWS KMS أو ما يعادلها)، ويُستخدم فوراً، ثم يُمحى من الذاكرة (Memory).

## 3. مشكلة رسوم الشبكة أثناء الكنس (Gas Fee Reserve)

**التحدي:** لكنس USDT من عنوان استقبال، تحتاج العملة الأساسية للشبكة لدفع الرسوم (مثال: كنس USDT-ERC20 يحتاج ETH بنفس العنوان لدفع الـ Gas). لكن عنوان الاستقبال أصلاً ما فيه غير USDT المُرسل من العميل!

**الحل المعياري — Gas Station Pattern:**
```
1. قبل أي عملية Sweep لعنوان يحتوي USDT فقط (بدون رصيد كافٍ من عملة الشبكة الأساسية):
2. النظام يرسل أولاً مبلغاً صغيراً جداً من عملة الشبكة الأساسية (من المحفظة التشغيلية Layer 2)
   إلى عنوان الاستقبال — يكفي فقط لتغطية رسوم عملية الكنس القادمة
3. بعد تأكيد وصول الرسوم → تُنفَّذ عملية كنس USDT كالمعتاد
4. الفائض الضئيل من عملة الشبكة الأساسية (إن وجد) يُكنس هو الآخر
```

> **ملاحظة خاصة لشبكة TRON (TRC20):** بدل إرسال TRX كرسوم في كل مرة، الأفضل معيارياً استئجار "Energy" مسبقاً على المحفظة التشغيلية (عبر خدمات Energy Rental مثل TronNRG) لخفض التكلفة الفعلية للكنس بشكل كبير — يُترك كخيار تحسين لاحق (Optimization)، وليس إلزامياً بالإصدار الأول.

## 4. سياسة العملات المتقلبة (Native Coin Volatility Policy)

USDT مستقرة القيمة، لكن العملات الأساسية (BTC, ETH, BNB, SOL, TON, TRX) متقلبة. لازم قرار واضح: هل نحتفظ فيها أو نحوّلها فوراً؟

**القرار المعتمد بالمعيار (افتراضي، قابل للتخصيص لاحقاً):**
- **USDT المستلمة:** تبقى USDT بالخزينة الباردة — لا تحويل، هي أصلاً الهدف.
- **العملات الأساسية المستلمة (دفعات فعلية من عملاء اختاروا الدفع بـ SOL/TON/BNB/ETH/TRX/BTC):** تحويل تلقائي فوري لـ USDT عبر DEX (Decentralized Exchange) على نفس الشبكة **فور الكنس للمحفظة التشغيلية**، لتفادي مخاطرة تقلب السعر على أموال العملاء المستلمة كدفعات.
- **الاستثناء:** مبالغ رسوم الشبكة المحتفظ بها بالمحفظة التشغيلية (Layer 2) للعمليات المستقبلية — تبقى بعملتها الأصلية لأنها "وقود تشغيلي" وليست إيراداً.

## 5. مخطط قاعدة البيانات

```sql
-- 1. المحافظ (تشغيلية آلية + احتياطي)
CREATE TABLE treasury_wallets (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    network_id INTEGER REFERENCES networks(id),
    asset_symbol VARCHAR(10) NOT NULL,
    tier VARCHAR(15) CHECK(tier IN ('OPERATIONAL', 'RESERVE')),
    address VARCHAR(255) NOT NULL,
    target_float_balance FLOAT,          -- الرصيد المستهدف (فقط للمحفظة التشغيلية)
    low_balance_alert_threshold FLOAT,    -- حد تحذيري لتنبيه الإدارة بضرورة تغذية يدوية
    UNIQUE(network_id, asset_symbol, tier)
);

-- 2. سجل عمليات الكنس (Sweep Log)
CREATE TABLE sweep_transactions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source_address VARCHAR(255) NOT NULL,        -- عنوان الاستقبال (Layer 1)
    destination_wallet_id INTEGER REFERENCES treasury_wallets(id),  -- عادة Hot Wallet
    network_id INTEGER REFERENCES networks(id),
    asset_symbol VARCHAR(10) NOT NULL,
    amount FLOAT NOT NULL,
    gas_funding_tx_hash VARCHAR(255),              -- تحويل رسوم التشغيل التمهيدي (Gas Station)، إن وُجد
    sweep_tx_hash VARCHAR(255),
    status VARCHAR(20) DEFAULT 'PENDING' CHECK(status IN ('PENDING', 'GAS_FUNDED', 'SWEPT', 'FAILED')),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    swept_at TIMESTAMP
);

-- 3. ترحيلات Hot → Cold
CREATE TABLE treasury_transfers (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    from_wallet_id INTEGER REFERENCES treasury_wallets(id),
    to_wallet_id INTEGER REFERENCES treasury_wallets(id),
    asset_symbol VARCHAR(10) NOT NULL,
    amount FLOAT NOT NULL,
    tx_hash VARCHAR(255),
    triggered_by VARCHAR(20) CHECK(triggered_by IN ('AUTO_THRESHOLD', 'MANUAL')),
    approved_by_user_id INTEGER REFERENCES users(id),  -- إلزامي لو MANUAL
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 4. طلبات السحب (لصرف عمولات المسوقين أو سحب الأرباح)
CREATE TABLE withdrawals (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    reference_type VARCHAR(30) NOT NULL,   -- 'AFFILIATE_PAYOUT', 'OWNER_WITHDRAWAL'
    reference_id INTEGER,
    destination_address VARCHAR(255) NOT NULL,  -- عنوان المستلم الخارجي (يُدخله المستفيد)
    network_id INTEGER REFERENCES networks(id),
    asset_symbol VARCHAR(10) NOT NULL,
    amount FLOAT NOT NULL,
    status VARCHAR(20) DEFAULT 'AUTO_APPROVED' CHECK(status IN
        ('AUTO_APPROVED', 'PENDING_APPROVAL', 'APPROVED', 'CANCELLED', 'BROADCASTING', 'COMPLETED', 'REJECTED', 'FAILED')),
    auto_approved_reason VARCHAR(50),        -- مثال: 'WITHIN_PER_TX_CAP', يُملأ فقط للسحوبات الآلية
    approved_by_user_id INTEGER REFERENCES users(id),  -- إلزامي فقط للحالات الاستثنائية (PENDING_APPROVAL → APPROVED)
    approved_at TIMESTAMP,
    scheduled_execution_at TIMESTAMP,        -- = approved_at + 24 ساعة، لا بث قبل هذا الوقت
    tx_hash VARCHAR(255),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    completed_at TIMESTAMP
);

-- 5. لقطة يومية لأرصدة الخزينة (لدعم التقارير والتدقيق)
CREATE TABLE treasury_balance_snapshots (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    snapshot_date DATE NOT NULL,
    network_id INTEGER REFERENCES networks(id),
    tier VARCHAR(10),
    asset_symbol VARCHAR(10),
    balance FLOAT NOT NULL,
    balance_usd_equivalent FLOAT NOT NULL,
    UNIQUE(snapshot_date, network_id, tier, asset_symbol)
);
```

## 6. القوانين الصارمة (Strict Rules)

### 6.1 قوانين حفظ المفاتيح (الأخطر على الإطلاق)
1. **ممنوع تخزين أي مفتاح خاص كنص صريح بقاعدة البيانات مهما كان السبب.** الـ Master Seed للمحافظ التشغيلية (Hot) يُخزَّن حصراً بخزينة أسرار مخصصة (Vault/KMS) مشفّرة بمفتاح منفصل تماماً عن قاعدة البيانات.
2. **مفتاح الخزينة الباردة (Cold) لا يُخزَّن رقمياً على أي سيرفر متصل بالإنترنت إطلاقاً.** يُحفظ فيزيائياً (ورقياً أو بجهاز Hardware Wallet مخصص) بمكان آمن خارج البنية التحتية الرقمية بالكامل.
3. **نسخة احتياطية من الـ Master Seed (Backup) إلزامية**، مخزّنة بمكان منفصل جغرافياً عن النسخة الأساسية، ومشفّرة بشكل مستقل.

### 6.2 قوانين الرصيد المستهدف والأتمتة
4. **الرصيد المستهدف (`target_float_balance`) إلزامي لكل (شبكة، عملة)** ويُحسب بهامش يغطي حجم السحوبات المتوقعة لعدة أيام (مثال: `متوسط السحوبات اليومية × 5`) — يُخزَّن كإعداد قابل للتعديل، وليس رقماً ثابتاً بالكود.
5. **سقف السحب الآلي لكل عملية (Per-Transaction Auto-Approval Cap):** أي طلب سحب فردي (استرجاع أو عمولة مسوّق) **بقيمة أقل من أو تساوي هذا السقف** (يُقترح: قيمة أعلى فئة اشتراك + هامش، مثال $75) يُنفَّذ **تلقائياً بدون تدخل بشري**.
6. **سقف السحب الآلي التراكمي اليومي (Daily Auto-Payout Cap):** إجمالي كل السحوبات الآلية بنفس اليوم لا يتجاوز حداً أقصى محدداً مسبقاً (مثال: $2,000). أي طلب يتجاوز هذا السقف التراكمي **يتحول تلقائياً لقائمة انتظار موافقة يدوية**، حتى لو كان المبلغ الفردي نفسه صغيراً.
7. **أي طلب سحب فردي يتجاوز `Per-Transaction Auto-Approval Cap` بمفرده** (حالة نادرة الحدوث بحكم طبيعة المبالغ الصغيرة، لكن ممكنة مستقبلاً) **يذهب إلزامياً لمسار الموافقة اليدوية**، بلا استثناء.
8. **فائض المحفظة التشغيلية فوق الرصيد المستهدف يُرحَّل تلقائياً لمحفظة الاحتياطي (Reserve)** بشكل دوري (كل كنس جديد يتحقق من هذا الشرط). **تغذية المحفظة التشغيلية من الاحتياطي عند النقص تبقى يدوية** (تنبيه للإدارة عند اقتراب الرصيد من حد أدنى تحذيري)، لتفادي أتمتة الاتجاهين معاً بنفس الوقت.

### 6.3 قوانين حالات السحب
6. **حالة `withdrawals` الافتراضية للسحوبات الصغيرة ضمن السقوف: `AUTO_APPROVED` مباشرة** (بدون `PENDING_APPROVAL`) — الأتمتة هي المسار الرئيسي بحكم صغر المبالغ. **فقط الحالات الاستثنائية** (تجاوز سقف العملية الفردية، أو تجاوز السقف التراكمي اليومي) تدخل حالة `PENDING_APPROVAL` وتنتظر تدخل بشري.
7. **يُشترط تسجيل `approved_by_user_id`** فقط بالحالات الاستثنائية اللي تصل فعلياً لمسار الموافقة اليدوية — للسحوبات الآلية، يُسجَّل بدلاً منه `auto_approved_reason` (أي قاعدة سمحت بالتنفيذ التلقائي)، لضمان مسار تدقيق كامل بكل الحالات.

### 6.3.1 قانون نافذة الانتظار الإلزامية (Hold Window)
9. **نافذة انتظار إلزامية (Withdrawal Hold Window) — 24 ساعة على كل سحب بلا استثناء**، حتى لو كان `AUTO_APPROVED` فوراً حسب سقوف الأمان. الموافقة (تلقائية أو يدوية) لا تعني التنفيذ الفوري — يُضاف حقل `scheduled_execution_at = approved_at + 24h`، والـ Worker المسؤول عن البث الفعلي على البلوكشين **لا ينفّذ أي سحب قبل هذا الوقت مهما كانت حالته**. هذا يعطي نافذة اكتشاف لأي خطأ أو نشاط مشبوه قبل أن تصبح العملية نهائية ولا رجعة فيها.
10. **إلغاء طلب السحب مسموح فقط خلال نافذة الـ 24 ساعة هذي** — إن اكتُشف خطأ (طلب مكرر، عنوان خاطئ، نشاط احتيالي) قبل انتهاء المهلة، يمكن لأي مستخدم إداري تغيير الحالة إلى `CANCELLED` ووقف التنفيذ نهائياً. بعد انتهاء المهلة وبدء البث، لا رجوع.
9. **كل حركة أموال (Sweep, Transfer, Withdrawal) يجب أن تحمل `tx_hash` قابل للتحقق على البلوكشين العام** — لا حركة أموال داخلية "منطقية فقط" بقاعدة البيانات بدون إثبات على السلسلة.
10. **لقطة يومية إلزامية (`treasury_balance_snapshots`) لكل الأرصدة عبر كل الطبقات والشبكات** — تُستخدم للتصالح المحاسبي (Reconciliation) اليومي: مجموع أرصدة الخزينة يجب أن يطابق (إيرادات الفواتير المؤكدة − السحوبات المكتملة − رسوم الشبكة المدفوعة) في أي لحظة.

### 6.5 قانون الفصل المعماري
11. **هذي الوحدة مستقلة تماماً عن منطق أي نظام مستهلك** (نظام التداول، الاشتراكات، إلخ) — أي نظام يحتاج صرف أموال (دفع عمولة مسوّق مثلاً) **يُنشئ طلب `withdrawal` فقط** عبر API، ولا يتدخل إطلاقاً بآلية الكنس أو الترحيل أو حفظ المفاتيح.

## 7. عقد الـ API لهذي الوحدة

```
GET    /api/treasury/balances                    → أرصدة كل الطبقات والشبكات اللحظية (للوحة تحكم الإدارة فقط)
POST   /api/withdrawals                           → طلب سحب جديد {reference_type, reference_id, destination_address, network_id, asset_symbol, amount}
POST   /api/withdrawals/:id/approve               → موافقة يدوية (صلاحية Admin فقط)
GET    /api/withdrawals?status=                   → قائمة طلبات السحب
GET    /api/treasury/reconciliation-report?date=  → تقرير التصالح اليومي
```

## 8. ملخص القرارات المعمارية الجديدة (محدَّث)

1. هيكلية مبسّطة: عناوين استقبال مؤقتة → محفظة تشغيلية آلية واحدة (برصيد مستهدف ثابت لكل عملة) → احتياطي يستقبل الفائض تلقائياً.
2. **السحوبات الصغيرة (استرجاع، عمولة مسوّق) تُنفَّذ تلقائياً بدون موافقة يدوية**، طالما ضمن سقف العملية الفردية والسقف التراكمي اليومي — مناسب لحجم مبالغ الاشتراكات الصغيرة (حتى $50).
3. سقف أمان مزدوج (فردي + يومي) يحوّل مخاطرة "اختراق يُفرِّغ كل شيء" إلى مخاطرة محدودة بحد أقصى معروف مسبقاً؛ أي تجاوز يتحول تلقائياً لموافقة يدوية استثنائية.
4. كنس تلقائي فوري بعد كل دفعة مؤكدة، مع حل "Gas Station" لتمويل رسوم الكنس.
5. العملات المتقلبة (غير USDT) تُحوَّل تلقائياً لـ USDT فور الكنس؛ USDT تبقى كما هي.

# قرار معماري: تسجيل الدخول عبر SuperAdmin حصراً (Centralized Auth / SSO)
## يُعدِّل قسم الأمان بوثيقة نظام تتبع التداول (v2) — يُطبَّق على كل نظام مستهلك مستقبلي

---

## 1. القرار

**تسجيل الدخول يكون عبر SuperAdmin فقط — لا يوجد أي نظام مستهلك (نظام التداول أو أي نظام مستقبلي) يبني جدول `users` أو صفحة تسجيل دخول خاصة به.**

بمعنى آخر: SuperAdmin يعمل كـ **موفّر هوية مركزي (Central Identity Provider)** بنمط شبيه بـ Single Sign-On — العميل يسجّل دخول مرة واحدة عبر SuperAdmin، ويستخدم نفس الجلسة للوصول لأي نظام مستهلك مشترك فيه، بشرط أن اشتراكه بذلك النظام تحديداً فعّال.

> **لماذا هذا هو القرار الصحيح:** هذا بالضبط سبب وجود "معيار موحّد" من الأساس — لو كل نظام مستهلك بنى مصادقته الخاصة، صرتم تكررون نفس منطق التشفير، الجلسات، 2FA، بكل مشروع جديد، وتفقدون أهم ميزة بالمعيار: **عميل واحد، حساب واحد، عبر كل منتجاتكم الحالية والمستقبلية.**

---

## 2. كيف تُفعَّليّاً يشتغل الربط بين SuperAdmin والنظام المستهلك

```
1. العميل يفتح نظام التداول (النظام المستهلك) بدون تسجيل دخول
        ↓
2. يُعاد توجيهه لصفحة تسجيل الدخول المركزية على SuperAdmin
        ↓
3. يسجّل دخول (بريد + كلمة مرور + 2FA إن مفعّل) — نفس آلية وحدة المستخدمين
        ↓
4. SuperAdmin يُصدر JWT قصير الأجل (Access Token، صلاحية 15 دقيقة)
   يحمل: user_id, role, subscription_status_for_this_system, exp
   + Refresh Token طويل الأجل (لتجديد الجلسة دون إعادة تسجيل دخول متكررة)
        ↓
5. العميل يُعاد توجيهه لنظام التداول مع الـ Access Token
        ↓
6. نظام التداول يتحقق من توقيع الـ JWT محلياً (بمفتاح عام مشترك JWKS)
   بدون أي استدعاء شبكة لـ SuperAdmin في كل طلب — تحقق Stateless سريع
        ↓
7. Middleware بنظام التداول (SubscriptionGuard) يفحص:
   - التوقيع صحيح؟
   - subscription_status_for_this_system = ACTIVE أو GRACE_PERIOD؟
   → لو الاثنين صح: يسمح بالوصول. لو لا: يُعاد توجيه لصفحة "اشتراكك غير فعّال"
```

---

## 3. لماذا Access Token قصير الأجل (15 دقيقة) تحديداً

**المشكلة لو كان طويل الأجل:** لو عميل ألغى اشتراكه أو انتهت مهلة السماح، والـ Token لسه ساري لساعات، بيستمر بالوصول للنظام رغم إن اشتراكه انتهى فعلياً.

**الحل:** Access Token قصير (15 دقيقة) + Refresh Token يجدده تلقائياً بالخلفية — **كل عملية تجديد تُعيد فحص حالة الاشتراك اللحظية من SuperAdmin**. يعني بأسوأ الحالات، العميل يفقد الوصول خلال 15 دقيقة كحد أقصى من لحظة انتهاء اشتراكه، بدون ما يحتاج النظام المستهلك يستعلم SuperAdmin بكل طلب.

---

## 4. القوانين الصارمة (Strict Rules)

1. **لا نظام مستهلك يخزّن `password_hash` إطلاقاً.** كلمة المرور تُخزَّن وتُدار حصراً بجدول `users` بوحدة المستخدمين على SuperAdmin. أي نظام مستهلك يحاول بناء صفحة "تسجيل دخول" خاصة به = خطأ معماري يخالف المعيار.
2. **الـ JWT يُوقَّع بخوارزمية غير متماثلة (RS256)** — SuperAdmin يملك المفتاح الخاص (يُوقِّع)، وكل نظام مستهلك يملك فقط المفتاح العام (يتحقق) — لا يقدر أي نظام مستهلك يُصدر Tokens مزوّرة حتى لو اختُرق جزئياً.
3. **حقل `subscription_status_for_this_system` بالـ JWT خاص بكل نظام على حدة** — عميل مشترك بنظام التداول فقط ما يقدر يدخل نظام ثاني ولو كان مسجّل دخول بنفس الحساب، إلا لو عنده اشتراك فعّال بذاك النظام تحديداً. الهوية موحّدة، لكن الوصول مقيّد بالاشتراك الفعلي.
4. **تسجيل الخروج من SuperAdmin يُبطل الـ Refresh Token فوراً** (يُضاف لقائمة إبطال قصيرة الأجل مطابقة لعمر أطول Refresh Token) — حتى لو Access Token الحالي لسه ساري لدقائق، الجلسة الكاملة تُقفل خلال أقصى 15 دقيقة.
5. **النظام المستهلك يحتفظ محلياً فقط بأي بيانات خاصة بمنتجه** (صفقات، محافظ، إلخ) مربوطة بـ `user_id` كمرجع خارجي — **لا نسخ أو تكرار لأي بيانات هوية** (البريد، كلمة المرور، 2FA) خارج SuperAdmin.

---

## 5. تعديل مطلوب على وثيقة نظام التداول (v2)

القسم 4 "نظام الحماية والأمان" بوثيقة نظام التداول الأصلية (جدول `users` المستقل، Bcrypt محلي، JWT مستقل) **يُلغى بالكامل** ويُستبدل بـ:

> نظام التداول لا يبني أي طبقة مصادقة خاصة به. يعتمد حصراً على التحقق من JWT صادر عن SuperAdmin (المفتاح العام يُضبط كإعداد بيئة عند التشغيل)، عبر Middleware واحد (`SubscriptionGuard`) يُطبَّق على كل المسارات المحمية. جدول `users` المحلي بقاعدة بيانات نظام التداول **يُحذف بالكامل** — يُستبدل بعمود `superadmin_user_id` (بدون FK فعلي عبر قاعدتي بيانات منفصلتين، فقط رقم مرجعي) يُضاف لجداول البيانات الخاصة (مثل `trades`, `exchanges`) لو احتجتوا لاحقاً تفصلوا بيانات كل عميل عن الثاني.

> **ملاحظة:** بما إن نظام التداول الحالي "مستخدم واحد" أصلاً (حسب القرار الأصلي)، هذا التعديل يبسّط الأمر عملياً — بدل ما تبنون نظام دخول كامل بالمرحلة الأخيرة، بس تتحققون من JWT صادر عن SuperAdmin وتخلص.

---

## 6. ملخص القرار

1. تسجيل الدخول والهوية = SuperAdmin حصراً، بلا استثناء لأي نظام مستهلك.
2. JWT قصير الأجل (15 دقيقة) + Refresh Token، توقيع غير متماثل (RS256) لمنع التزوير.
3. حالة الاشتراك تُفحص لكل نظام مستهلك على حدة داخل الـ Token نفسه.
4. الأنظمة المستهلكة تربط بياناتها بـ `user_id` مرجعي فقط — صفر تكرار لمنطق أو بيانات المصادقة.
5. وثيقة نظام التداول (v2) تحتاج تعديل: حذف قسم الأمان المستقل بالكامل، استبداله بالتحقق من JWT مركزي.

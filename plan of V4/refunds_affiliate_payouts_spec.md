# وحدة الاسترجاع النقدي وصرف عمولات المسوقين (Refunds & Affiliate Payouts)
## جزء من المعيار الموحّد (Standard Architecture)

> **العلاقة بالوحدات السابقة:** كلا التدفقين هنا ينتهيان بنفس نقطة النهاية: إنشاء سجل بجدول `withdrawals` (المعرَّف بوثيقة الخزينة) يمر بنفس آلية الموافقة اليدوية الإلزامية. الفرق بينهما هو **كيف يُحسب المبلغ ومتى يحق للطرف طلبه** — وهذا ما تُغطيه هذي الوثيقة.

---

## القسم الأول: الاسترجاع النقدي (Refunds)

### 1. لماذا الاسترجاع بالكريبتو مختلف جذرياً عن البطاقات

بالدفع التقليدي (بطاقة ائتمان)، الاسترجاع تلقائي لنفس البطاقة. **بالكريبتو هذا غير ممكن تقنياً** — عنوان الاستقبال أصلاً عنوان مؤقت مُولَّد للفاتورة، وقد يكون العميل دفع من محفظة تبادل (Exchange) لا تقبل استرجاعات مباشرة أصلاً. لذلك:

> **قاعدة أساسية:** الاسترجاع **يتطلب من العميل تزويد عنوان محفظة وجهة (Destination Address) بنفسه** وقت طلب الاسترجاع — لا يوجد "استرجاع تلقائي لمصدر الدفع".

### 2. سياسة الاسترجاع (Refund Policy) — قابلة للتخصيص لكل نظام مستهلك

| الحالة | القاعدة الافتراضية بالمعيار |
|---|---|
| إلغاء خلال فترة سماح (مثال: 3 أيام من الدفع) ولم يُستخدم الاشتراك فعلياً | استرجاع كامل 100% |
| إلغاء بعد استخدام جزء من فترة الاشتراك | استرجاع تناسبي (Pro-rated) = `(الأيام المتبقية / إجمالي أيام الدورة) × المبلغ المدفوع` |
| إلغاء بعد انتهاء فترة السماح بالكامل | لا استرجاع (حسب سياسة كل نظام مستهلك — قابلة للتخصيص) |

> **ملاحظة معيارية:** هذي القيم (فترة السماح، هل التناسب مفعّل) تُخزَّن كإعدادات على مستوى كل نظام مستهلك (Tenant Config)، وليست ثابتة بالكود، لأن سياسة الاسترجاع تختلف حسب طبيعة كل منتج.

### 3. حساب مبلغ الاسترجاع بالكريبتو — قاعدة التسعير الحرجة

```
1. المبلغ المستحق يُحسب دائماً بالدولار أولاً (refund_amount_usd) بناءً على سياسة الاسترجاع أعلاه
2. عند تنفيذ التحويل الفعلي، يُستخدم سعر الصرف اللحظي وقت التنفيذ (وليس سعر الفاتورة الأصلية وقت الدفع)
3. رسوم الشبكة (Network Fee) لعملية الاسترجاع تُخصم من مبلغ الاسترجاع نفسه افتراضياً
   (قابل للتغيير: يمكن اعتماد "تحمّل الشركة للرسوم" كإعداد بديل)
```

> **مثال:** عميل دفع ما يعادل $100 عبر USDT-TRC20، ألغى الاشتراك بعد استخدام 50% من الدورة → `refund_amount_usd = $50`. وقت تنفيذ الاسترجاع الفعلي، تُرسل $50 من USDT (مطروحاً منها رسوم الشبكة البسيطة على TRC20) لعنوان المحفظة اللي زوّده العميل.

### 4. مخطط قاعدة البيانات — الاسترجاع

```sql
CREATE TABLE refunds (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    subscription_id INTEGER NOT NULL,             -- مرجع للاشتراك الملغى (بالنظام المستهلك)
    original_invoice_id INTEGER REFERENCES invoices(id),
    refund_amount_usd FLOAT NOT NULL,
    refund_reason VARCHAR(50) CHECK(refund_reason IN
        ('GRACE_PERIOD', 'PRO_RATED_CANCELLATION', 'SERVICE_ISSUE', 'MANUAL_ADJUSTMENT')),
    customer_destination_address VARCHAR(255) NOT NULL,  -- يُدخله العميل عند طلب الاسترجاع
    network_id INTEGER REFERENCES networks(id),           -- الشبكة التي يريد العميل الاستلام عليها
    asset_symbol VARCHAR(10) NOT NULL DEFAULT 'USDT',
    withdrawal_id INTEGER REFERENCES withdrawals(id),      -- الرابط بينه وبين تنفيذ السحب الفعلي
    status VARCHAR(20) DEFAULT 'REQUESTED' CHECK(status IN
        ('REQUESTED', 'APPROVED', 'PROCESSING', 'COMPLETED', 'REJECTED')),
    requested_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    approved_by_user_id INTEGER REFERENCES users(id)
);
```

### 5. تسلسل العمل (Refund Flow)

```
1. العميل/الإدارة يطلب استرجاع لاشتراك معيّن → POST /api/refunds
2. النظام يحسب refund_amount_usd تلقائياً حسب سياسة الاسترجاع (جدول أعلاه)
3. العميل يُدخل عنوان محفظته للاستلام + يختار الشبكة
4. حالة الطلب → REQUESTED (بانتظار موافقة إدارية إلزامية، بلا استثناء)
5. عند الموافقة → يُنشأ سجل بجدول withdrawals تلقائياً (reference_type='REFUND', reference_id=refund.id)
   ويمر بنفس مسار السحب المعرَّف بوثيقة الخزينة (موافقة → بث → تأكيد)
6. عند اكتمال السحب على البلوكشين → refunds.status = COMPLETED، والاشتراك يتحول لحالة CANCELLED نهائياً بالنظام المستهلك
```

### 6. قوانين صارمة — الاسترجاع

1. **لا يُلغى الاشتراك فعلياً (حالة `CANCELLED` النهائية) قبل اكتمال الاسترجاع فعلياً على البلوكشين** — يبقى بحالة وسيطة (`PENDING_REFUND`) لمنع تكرار طلبات الاسترجاع لنفس الاشتراك.
2. **عنوان الاسترجاع يجب أن يمر بتحقق صيغة (Address Validation) قبل القبول** — استخدام `NetworkAdapter.validateAddress()` المعرّفة بوحدة الدفع، لتفادي إرسال أموال لعنوان غير صالح (خسارة نهائية).
3. **أي استرجاع فوق حد معيّن بالدولار (يُحدَّد كإعداد، مثال $500) يتطلب موافقتين إداريتين منفصلتين (Two-person approval)** بدل موافقة واحدة، لتقليل مخاطرة الاستغلال الداخلي.

## القسم الثاني: صرف عمولات المسوّقين (Affiliate Payouts)

### 7. دورة حياة العمولة — من التسجيل إلى الصرف

```
عميل جديد يشترك عبر رابط مسوّق
        ↓
عند تأكيد دفع الفاتورة الأولى (invoice.status = PAID)
        ↓
يُنشأ سجل affiliate_commissions (نوع: INITIAL) تلقائياً — حالة: PENDING_CLEARANCE
        ↓
بعد فترة سماح (Clearance Period) — **افتراضياً شهر تقريباً (30 يوماً) من تاريخ دفع العميل المُحال**، وليس أياماً قليلة — لضمان تجاوز أي نافذة استرجاع محتملة بأمان قبل اعتبار العمولة نهائية
        ↓
الحالة تتحول → CLEARED (متاحة للسحب الآن، تُضاف لرصيد المسوّق القابل للسحب)
        ↓
عند طلب المسوّق السحب: يمر بنفس نافذة الانتظار الإلزامية 24 ساعة المعرَّفة بوثيقة الخزينة (حتى لو السحب مُوافَق عليه تلقائياً) قبل التنفيذ الفعلي على البلوكشين
        ↓
عند كل تجديد لاحق لنفس العميل (إن كانت الاستراتيجية Recurring) → يتكرر نفس المسار (نوع: RECURRING)، بنفس فترة السماح الشهرية لكل دورة على حدة
```

> **لماذا فترة السماح (Clearance Period) إلزامية ولماذا شهر تحديداً:** لو صُرفت العمولة فوراً عند الدفع، وطلب العميل استرجاعاً بعدها، تصير الشركة قد دفعت عمولة على إيراد لم يعد موجوداً. فترة سماح شهرية تغطي عملياً كامل دورة الاشتراك الشهري الأولى، فلا تتحول العمولة لـ `CLEARED` إلا بعد التأكد الفعلي إن العميل استمر ولم يُلغِ. المدة قابلة للتعديل كإعداد بالنظام، وليست ثابتة بالكود.

### 8. مخطط قاعدة البيانات — العمولات

```sql
-- 1. دفتر أستاذ العمولات (Commission Ledger)
CREATE TABLE affiliate_commissions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    affiliate_user_id INTEGER NOT NULL,             -- المسوّق المستفيد
    referred_customer_id INTEGER NOT NULL,           -- العميل الذي جلبه
    source_invoice_id INTEGER REFERENCES invoices(id), -- الفاتورة التي ولّدت العمولة
    commission_type VARCHAR(10) CHECK(commission_type IN ('INITIAL', 'RECURRING')),
    commission_pct FLOAT NOT NULL,                    -- النسبة المطبّقة وقت الاحتساب (تُجمَّد، لا تتغير لاحقاً)
    commission_amount_usd FLOAT NOT NULL,
    status VARCHAR(20) DEFAULT 'PENDING_CLEARANCE' CHECK(status IN
        ('PENDING_CLEARANCE', 'CLEARED', 'REVERSED', 'PAID_OUT')),
    clearance_at TIMESTAMP,                            -- وقت انتهاء فترة السماح
    reversed_reason VARCHAR(30),                        -- 'CUSTOMER_REFUNDED', 'FRAUD_DETECTED'
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 2. رصيد المسوّق المجمّع (Materialized Balance — للأداء، يُحدَّث بـ Trigger أو Job)
CREATE TABLE affiliate_balances (
    affiliate_user_id INTEGER PRIMARY KEY,
    available_balance_usd FLOAT DEFAULT 0.0,   -- CLEARED وغير مسحوبة بعد
    pending_balance_usd FLOAT DEFAULT 0.0,      -- PENDING_CLEARANCE
    lifetime_paid_usd FLOAT DEFAULT 0.0,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 9. قوانين صارمة — العمولات والصرف

4. **عكس العمولة (Reversal) إلزامي تلقائياً عند الاسترجاع:** أي `refund` مكتمل مرتبط بفاتورة ولّدت عمولة سابقة (`PENDING_CLEARANCE` أو `CLEARED` ولم تُصرف بعد) → تتحول العمولة تلقائياً لحالة `REVERSED` وتُخصم من `pending_balance_usd` أو `available_balance_usd` فوراً. **لو كانت العمولة صُرفت فعلياً (`PAID_OUT`) قبل الاسترجاع** — لا استرجاع تلقائي منها (تُدار كحالة استثنائية يدوية، لتفادي تعقيد "دين على مسوّق").
5. **حد أدنى للسحب (Minimum Payout Threshold) إلزامي** (مثال: $20) — لتفادي طلبات سحب متناهية الصغر تُهدر قيمتها بالكامل برسوم الشبكة. يُعرض للمسوّق رصيده المتاح، لكن زر "طلب السحب" يبقى معطّلاً تحت هذا الحد.
6. **طلب السحب من المسوّق يُنشئ سجل `withdrawals`** بـ `reference_type='AFFILIATE_PAYOUT'`, `reference_id=affiliate_user_id` — يمر بنفس مسار الموافقة الإلزامية المعرَّف بوثيقة الخزينة، بدون أي استثناء أو "مسار سريع" حتى لو المبلغ صغير.
7. **نسبة العمولة (`commission_pct`) تُجمَّد وقت احتساب كل سجل عمولة على حدة** — لو الإدارة غيّرت نسبة العمولة العامة لاحقاً، العمولات المُحتسبة سابقاً **لا تتأثر بأثر رجعي**، فقط العمليات الجديدة تطبّق النسبة الجديدة.
8. **دورة Recurring مرتبطة إلزامياً بحالة الاشتراك الفعلية:** لو العميل المُحال ألغى اشتراكه، عمولات `RECURRING` المستقبلية لهذا العميل تتوقف تلقائياً من الاحتساب من جذرها (لا سجل يُنشأ أصلاً)، وليس فقط "لا تُصرف".

### 10. عقد الـ API

```
POST   /api/refunds                              → طلب استرجاع {subscription_id, destination_address, network_id}
GET    /api/refunds/:id/status

GET    /api/affiliates/:id/balance                → الرصيد المتاح/المعلّق للمسوّق
GET    /api/affiliates/:id/commissions             → سجل العمولات التفصيلي
POST   /api/affiliates/:id/payout-request          → طلب سحب (يُرفض تلقائياً لو أقل من الحد الأدنى)
```

## 11. ملخص القرارات المعمارية الجديدة

1. الاسترجاع يتطلب عنوان وجهة من العميل يدوياً (لا استرجاع تلقائي لمصدر الدفع كالبطاقات).
2. مبلغ الاسترجاع يُحسب بالدولار دائماً، ويُنفَّذ بسعر الصرف اللحظي وقت التنفيذ لا وقت الدفع الأصلي.
3. فترة سماح إلزامية (Clearance Period) قبل تحول أي عمولة لقابلة للسحب، لتفادي التعارض مع استرجاعات لاحقة.
4. عكس تلقائي للعمولات غير المصروفة عند حدوث استرجاع مرتبط بها.
5. حد أدنى إلزامي لطلبات سحب المسوقين لتفادي إهدار القيمة برسوم الشبكة.
6. كلا التدفقين (استرجاع وصرف عمولة) ينتهيان إلزامياً بنفس مسار موافقة `withdrawals` — لا مسارات مختصرة.

---

بهذا اكتملت حلقة الأموال كاملة: استقبال ← حماية/خزينة ← استرجاع ← صرف عمولات. الوحدات المتبقية بالمعيار: الاشتراكات نفسها (دورة الحياة، التجديد، الفوترة الاستباقية)، المستخدمين، صفحات الهبوط.
